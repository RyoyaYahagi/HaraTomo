# HaraTomo UX

## 1. UXの目的

HaraTomoのUIは、ユーザーに「管理画面を操作している」と感じさせるのではなく、**思い出したことをすぐ記録し、必要なときだけ振り返れること**を優先する。

主なUX目標:

- 入力開始まで迷わせない
- 一度に多くの判断を要求しない
- AIが整理した内容を簡単に確認できる
- 曖昧な箇所だけ修正できる
- 記録とAIの推測を視覚的に混同させない
- 症状の原因を断定しているように見せない

## 2. 基本フロー

```text
Home
  ↓
自然文を入力
  ↓
AI processing
  ↓
Confirmation
  ├─ 問題なし → Save
  └─ 修正あり → Edit → Save
  ↓
Timeline
  ↓
必要なら Event Detail / Insight
```

ユーザーに最初から event type、severity、context を個別入力させない。

## 3. 画面設計

### 3.1 Home / Record

#### 目的

最短で記録を開始する。

#### Primary Action

**記録する**

#### 必須要素

- 短い入力ガイド
- 自然文入力欄
- 記録ボタン
- 最近の記録への導線

例:

```text
今日どうだった？

[ 昼にラーメン。夕方冷えて、20時に腹痛… ]

                         記録する

最近の記録
今日 20:00  腹痛
今日 12:30  ラーメン
```

#### 置かないもの

- 統計カードの大量表示
- 複数のPrimary Button
- 最初から表示される詳細フォーム
- AI機能一覧
- 将来機能への大きな導線
- 「ダッシュボードらしくする」ためだけのKPI

HomeはDashboardではなく、**記録開始地点**として扱う。

### 3.2 Processing

#### 目的

処理中であることを伝え、不安にさせない。

#### 表示

- 簡潔な進行表示
- 入力したraw text

内部のLLM / Jev / Zod処理をユーザー向けに逐一表示しない。

### 3.3 Confirmation

#### 目的

AIが整理した内容を、保存前に短時間で確認する。

#### Primary Action

**この内容で保存**

#### 表示

Event候補を時系列順に並べる。

```text
12:30
食事
ラーメン

18:00
生活
冷え

20:00
症状
腹痛 6/10
```

修正が必要な項目だけ直接編集できる。

#### 原則

- すべてをフォーム化しない
- AI confidenceの数値を通常ユーザーへ見せない
- Jevの確率を医学的確信度のように見せない
- 曖昧な項目だけ注意表示する
- raw textへ戻れるようにする

### 3.4 Timeline

#### 目的

「いつ、何があったか」を素早く把握する。

#### Primary Action

原則なし。閲覧を主目的とする。

#### 表示

日付ごとの連続したリストを基本とする。

```text
9月24日

20:00  腹痛 · 6/10
18:00  冷え
12:30  ラーメン

9月23日

21:00  膨満感
19:00  カレー
```

EventごとにCardを作らない。余白・文字階層・dividerでグループを表現する。

### 3.5 Event Detail / Edit

#### 目的

1件の記録を確認・修正・削除する。

#### Primary Action

編集時のみ **保存**

#### 表示

- occurred_at
- type
- label
- normalized label（必要時）
- severity（症状のみ）
- note
- raw text（必要時）

削除はdestructive actionとしてPrimary Actionから離す。

### 3.6 Simple Insight

#### 目的

症状の前に記録されていた出来事を振り返る。

#### 表現

「原因」ではなく「一緒に記録されていたこと」「症状前6時間に多かったもの」と表現する。

例:

```text
腹痛の前6時間によく記録されていたもの

冷え       4 / 7回
コーヒー   3 / 7回

7件の腹痛記録をもとに集計
```

因果関係を示唆する矢印、危険度、診断ラベルは使わない。

## 4. ナビゲーション

MVPではナビゲーションを増やしすぎない。

候補:

- 記録
- 履歴
- 振り返り

3項目程度から始める。

設定・プロフィール・AI Askなど、未実装機能の空タブを先に作らない。

## 5. Mobile First

主な利用場面は食後・症状発生時の短時間入力を想定する。

- まず375px前後の幅で成立させる
- desktopでは情報を横に増やすのではなく、読みやすい最大幅を保つ
- 主要操作は親指で押しやすいサイズにする
- hoverだけに情報を依存しない

## 6. 状態設計

### Empty

説明を増やしすぎず、最初の記録方法を1つ示す。

### Loading

skeletonを大量に並べない。処理対象が小さい場合は簡潔なprogress表示でよい。

### Error

技術用語を出さない。

- raw textを失わない
- 再試行できる
- 必要なら手動修正へ進める

### AI ambiguity

「AIが間違っています」ではなく、確認してほしい箇所を具体的に示す。

## 7. AIとの役割分担をUIにも反映する

ユーザー入力:
- 本人が記録した事実

AI整理:
- Event候補
- normalized label
- 追加確認候補

Code:
- 時間差
- 件数
- 6時間window
- 集計

画面上でも、AI推測をユーザー自身の入力と同じ確度で表示しない。

## 8. 1画面1目的

各画面はPrimary Actionを原則1つにする。

UIが複雑になった場合、最初に「何を追加するか」ではなく以下を確認する。

1. この画面でユーザーが今やることは何か
2. それ以外の情報は今必要か
3. 別画面・detail・progressive disclosureへ移せないか

## 9. UX完了条件

新しい画面を実装するとき、最低限以下を満たす。

- 画面の目的を1文で説明できる
- Primary Actionが1つ以下
- Primary Actionまで迷わず到達できる
- 不要なCardがない
- 同じ情報を複数箇所で重複表示していない
- empty / loading / errorが必要な場合にだけ存在する
- AIが原因や医学的判断を断定していない
